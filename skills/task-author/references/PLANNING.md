# Planning details and decisions

Read on demand from `SKILL.md` (task-author). Moved here verbatim; the rules are unchanged.

## Sprint, assignment, scope fields, task fields

- **Sprint.** Only when the user asks: group the tasks by dependency order and ask the sprint length.
- **Assignment** (informational; the run flow ignores it): specialty match first; `L` and risky tasks to a senior; balanced load per person; one sentence of reason per assignment.
- **Scope, patterns, response, priority, origin (A202).** Optional, only what the user gave: `## Allowed scope` and `## Forbidden scope` (bullets: file, folder or glob; the freeze refuses a plan path inside Forbidden scope and nothing waives it; a plan path outside Allowed scope is asked in the batch pre-flight), `## Existing pattern references` ("do it like this file": the explorer reads them first, the plan must name each and review checks conformity), `## Completion response` (the final summary format the user wants; the lead's last message and the completion report follow it), front matter `priority: high|medium|low` (batch order among tasks without dependencies). A task born from another task's observation or exemption, or from a PRD requirement, gets its source written by `node <skill-dir>/scripts/link-origin.mjs <task.md> --from <TASK-ID>` or `--prd <slug>` (front matter `origin:` plus a row in `links.tsv`; the source file is not edited). Never invent these; ask.
- **Task fields.** Optional: `size` (S|M|L), `sprint` (positive integer or label), `assignee` (role label, never a name), `depends_on` (list of task ids), `prd` (slug of the PRD the `Covers:` ids refer to), `type` (`feature`, `bug`, `refactor`, `content`, `docs` or `chore`; an unknown value is rejected; `defect` is still read as the old spelling of `bug` and warned about). In the markdown target they are a YAML block (`---` ... `---`, same keys) right after the `# Task:` line (and after a `**Status:**` line when there is one) with a blank line between, so line 1 stays the H1; put a blank line before the closing `---` so Markdown does not render the last key as a heading (a leading block in a hand-written file is also read); `validate-task.mjs` rejects an unknown size and a `depends_on` id with no task file in the tasks directory (`--tasks-dir DIR`; default the task's own directory, plus its parent when the file is named `TASK.md`). Before approval the sibling drafts are not in `tasks.dir` yet, so validate the draft batch with `--tasks-dir` pointing at the draft folder under `.agents/local/task-author/<slug>/`; with `local_state: off` write the batch to a `mktemp -d` directory outside the repository (shared rule 13) and point `--tasks-dir` there, removing it afterwards. In `github`, `jira`, `linear` map `sprint` to the milestone and `assignee` to the assignee where the tracker has them; otherwise add a `Planning:` line to the description.

## Decisions and ADRs

Decisions are either task-level (they stay in the task: criteria, constraints, out of scope) or project-level (tech stack, content structure, language support, publishing, architecture patterns). `intent-grill` marks each one ([INTENT-FORMAT.md](../intent-grill/references/INTENT-FORMAT.md)); do the split from that mark. After the user's approval, write each project-level decision as an ADR in `design_docs.adr_dir` following `system-design`'s `references/ADR.md` (context, decision, rationale, rejected alternatives), `NNNN` = highest existing number + 1. A decision that contradicts an existing ADR becomes a NEW ADR and the old one's Status line is set to `superseded by NNNN`; an ADR is never silently overwritten. Each task file links the ADRs it relies on under `## Context` with a root-relative link (`/docs/adr/0001-x.md`), which survives the move to `in-progress/` and the run copy. No new decision store. In a run the `system-design` rules stay (proposed under `design/adr/`, the knowledge step moves them); this standalone rule is the extra one.
