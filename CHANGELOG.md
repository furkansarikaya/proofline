# Changelog

## Unreleased

- The freeze accepts a destructive step in phase `contract` (a separate, later migration file) as well as `deferred` (A141, amends A52, A55, A137): the plan the data architect writes for a user who wants the column and its data gone no longer stalls in PLANNING. A destructive step in expand, backfill or switch, `single_step` without the task's wording, and the destructive approval after FREEZE are unchanged.
- New skill `docs-writer` and a shared writing profile (A138): `/proofline docs create|update|audit` writes, updates from a diff and audits documentation; `scripts/check-docs.mjs` proves that quoted links, paths, flags, subcommands and config keys exist (`doc:line: kind not found: claim`); new config block `writing: { profile: auto|ste|plain, strictness: relaxed|strict }` validated by `config-check`; `tests/shared/check-writing.mjs` measures sentence and paragraph length (warnings under `relaxed`, exit 1 under `strict`) and `tests/shared/check-shared.sh` keeps the per-skill copies identical; the knowledge step runs docs `update` when user-visible behaviour changed. The architect role carries the skill; no new role, gate or state.
- A request that already says the data is not wanted and the column should go no longer stalls in intake (A137, amends A131, A32, A55): the task author no longer defers the drop as the recommended option, asks whether or when to drop, or refuses the drop criterion once the user stated the intent; it writes the whole removal as criteria and the data architect plans the drop as a `contract` step (a later migration) behind the destructive approval. The explicit-statement rule applies only when the user's own words say the data is not wanted and the column should go; hedged or inferred wording still gets the data-fate question. `question.CRITICAL.txt` is unchanged. Found by a CRITICAL regression run that asked the same question three times. No EXPECTED item or safety rule changed.

- A full approval sentence approves, for every approval kind, and approval stays fail-closed (A134, amends A108): `I approve the plan`, `Planı onaylıyorum`, `I approve the commit`, `commit'i onaylıyorum`, `I approve the scope`, `kapsamı onaylıyorum` and the equivalents for destructive, single_step, budget, push and waive (with the finding id), Turkish ASCII variants included, optionally with `for <ID>` / `<ID> için`; the whole reply must equal one sentence of the kind, so hedged, negated, mixed, question, wrong-kind and empty answers, and a sentence quoted inside other text, are still re-asked (a reply that is only the quoted sentence still approves); the approval question shows the full sentence.
- End-to-end expectations are tagged `[invariant]` or `[quality]`; a scenario passes when all invariant items are met and at least 90% of the quality items are met, and the evaluator's verdict line reports both counts (A133, amends A95, A131). C-14 allows at most 3 answers, +1 for every refreeze (plan approvals, harness replies and question replies together). `tests/e2e/README.md` no longer lists C-14 as an open item. No item was removed or loosened; quality items: F-9, X-3, X-9, K-4.
- A Codex lead runs on the base model, never the cheapest (A135, amends A100): `execution_policy.lead_base_model.codex: gpt-6-sol` in the policy table; new `exec-policy.sh check-lead` refuses a lead model below base (`LEAD_BELOW_BASE`, naming the base model) and an unset model (`LEAD_MODEL_UNSET`); an installed config without the key falls back to a base derived from the ladder and the lead tier floor; the e2e harness defaults a Codex lead to the base model and applies the check to the first `codex exec`, `codex exec resume` and the FAILOVER resume (`E2E_CODEX_MODEL=gpt-6-luna` for a lead now exits 2); `proofline doctor` reports a Codex lead resolving below the base and warns when `lead_base_model` is missing. Codex workers and mixed runs keep the cheap model.
- Merging requires green CI, enforced on the merge path (A136): new `proofline merge <PR> [--merge|--squash|--rebase] [--delete-branch] [-R OWNER/REPO]` (`bin/lib/merge.sh`) reads the pull request fresh with `gh pr view`, refuses unless it is open, not a draft and every check run is COMPLETED/SUCCESS and every status SUCCESS (pending, failed, cancelled, neutral, no checks, unparsable output, gh or jq missing, offline: refused with what was seen; a skipped check passes only when not required), re-reads the head SHA right before the merge and merges with `--match-head-commit`; `--admin` and `--auto` are always refused. The PreToolUse hook denies every other merge path for every caller, run or not, installed project or not: `gh pr merge` in any spelling, merge endpoints and mutations of `gh api`, `gh alias`, `git push` of a protected branch, `git merge` on one. New `tests/enforcement/merge-guard-test.sh` with a stubbed `gh`. CONTRIBUTING "Merge when CI is green" now says it is checked by script for the common spellings, with GitHub branch protection as the backstop. Review round 1: a push dry-run is honoured only for a real `-n`/`--dry-run` (not the value of `-o`); a variable or substitution where the gh subcommand goes, `curl`/`wget`/`http`/`xh` at GitHub merge/refs/contents/graphql, `gh api --input`/`=@file`/mutations/contents writes, merge text piped or passed to a shell, interpreter, eval or git alias, and unreadable directories (`cd -`, `env -C`, `GIT_DIR`) are denied; `PATH=` on a gh command is denied; the wrapper prints the gh it uses, refuses a shadowed gh/jq or an empty PATH entry, and always requires every `gh pr checks --required` check to be present in the rollup and a pass.
- Documentation: every statement of test or end-to-end results is current and dated. `tests/e2e/README.md` has a "Current results" section (last passing run per scenario with date and `main` commit, the regression round of 2026-10-17, the run history, the Codex and mixed integration checks, known limits and the open C-14 question); the README "Support levels" table shows per scenario the last passing run and the decisions merged after it (nothing is plainly "passing" on the current `main`), "Capabilities and what tests them" names the capabilities that team runs exercised, `adapters/README.md` has a support table, the daily-use guide (and its Turkish translation) states what is verified, CONTRIBUTING quotes current test counts and CI time and its checklist asks for dated results, and the sample app's `package.json` version is 0.0.1. No behaviour change, no EXPECTED file changed.

EXPECTED files unchanged.

- The e2e harness answers the second plan approval a refreeze asks for (A128, amends A95, A120): `pending-kind.sh` reads the newest `approvals/NNN-request-<kind>.yaml` when `agent.sh next` names no approval, only exactly `plan` is answered (every other kind, `waive:<ID>` included, stops unanswered; `reply-decision.sh`), the commit/push guard no longer matches the accepted-answers line (English or Turkish) of an approval question, and the reply cap ends the run with `stopped=max-replies` in `summary.txt`.
