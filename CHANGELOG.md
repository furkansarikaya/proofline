## 0.0.201 — 2026-11-27

- Feature (A380, issue 338 U7 and C3, the parts A368 and A361.1 deferred): page kinds. The UI spec (`ui.json`) and the visual-proof config may list `page_kinds` (`{ kind, paths: [glob], text_only?, reason }`); measure.mjs copies the list into `report.json`. (1) Text-only profile: a page of a kind declared `text_only` is not asked for the hero (`design_empty_hero`), the motion layer (`design_motion_count`) and the image ledger (`design_image_ledger`, only without a self-hosted font) when its measured facts show no visual medium or background image of 80 px or more, no hero visual, no raster image and no motion at any design viewport; those items are `not_applicable` with a fixed note, the page entry records the evidence (`text_only`), and the validator refuses the note anywhere the report does not back it. A declared page that shows a visual, an image or motion, and every page not declared text-only, is measured exactly as before. No new approval kind. (2) Standing approvals of measured visual items: a failed measured item of the QA visual report (`touch_target`, `design_empty_hero`, ...) that you waive with `standing` is kept as one row per check, threshold and page kind (or page, when it has no kind), with the worst value of the waived group; the request shows the kind, its paths and the value. It is carried only for the same check and threshold, a value no worse, and a page the report declares of that kind whose path matches the glob you were shown; a worse value, another kind or a page outside the glob is asked again. Only the rows the request showed are kept: a visual report rewritten between the request and the waiver keeps nothing (the waiver is for that run only). `design_raw_markup`, `raw-markup-in-text` (A368) and `design_image_ledger` (its value counts images) are never carried. Page globs are matched in linear time and have at most 16 wildcards; the root page's path is `/`. `agent.sh standing list` and `revoke <check>` work on these rows like the others.

## 0.0.195 — 2026-11-26

- Feature (A373, issue 338 C10 = R1-17, R2-17): the known-vulnerability check of the SECURITY dependencies focus runs once instead of never. With `security.advisory_check: on` (your hand edit, default off: your one-time consent, because it sends the package names and versions of the lock file to `registry.npmjs.org` over HTTPS) the new lead command `agent.sh advisory-check <ID>` parses the root `package-lock.json` or `npm-shrinkwrap.json` as JSON (a regular file up to 16 MiB; no npm, no project script and no project config runs or is read), validates every `node_modules/<name>` entry against the npm name and semver grammars, and makes one bulk POST per batch of at most 500 packages (at most 5000 packages and 10 requests; a redirect, timeout or non-200 answer is a failure; no proxy is used, so a proxy-only network records a failed request (`network error`), never a clean result). The answer is reduced to ids, packages, severities and a few bounded strings. It writes `ADVISORY_CHECK.json` with a ledger row (one counted request set per lock content, at most three attempts per lock content and six sets per run). The security role stays network-blocked and reads it through `validate-dependencies.mjs --advisory`: a high or critical advisory in a dependency the diff added or changed is a blocking finding for the reviewer, other advisories are info rows. Entries that cannot be checked (links, git or file specs, invalid names) are counted and shown, and too many make the record `partial`; every package name, private scoped ones included, goes to the public registry, so users with private packages should leave the setting off. Only npm locks for now (pnpm, yarn, bun and other ecosystems keep the "not checked" row); no offline advisory database.
